SFTDataset 类全图解

SFT（有监督微调）和 CT（继续预训练）唯一的核心差别，其实就是 labels[:n_pre].fill_(-100) 这一行。
class SFTDataset(Dataset) common/sft_data.py L28-L92 被 Lab3（全参 SFT）和 Lab4（LoRA SFT）共用，保证两者数据处理一致、对比公平

一句话职责：把一条 JSON 对话（messages 列表）编码成模型可训练的 input_ids / labels，并且「只对 assistant 的回答部分算 loss，system/user 部分全部用 -100 遮蔽掉」。

一、CT vs SFT：一张图看懂为什么要 mask

CT（继续预训练）labels = input_ids 原样

整条序列每一个 token 都要预测"下一个 token"，不分角色。

System prompt
User 提问
Assistant 回答

input_ids：每个位置都参与 loss 计算。模型甚至会被训练去「学习怎么生成用户的提问」——浪费容量。

VS

SFT（有监督微调）prompt 部分填 -100

只让 assistant 段算 loss，前半段完全不参与梯度。

Mask (-100，不算 loss)
训练目标

labels：只有 assistant 回答段是真实 token id，前面全是 -100。F.cross_entropy 遇到 -100 自动跳过。模型容量 100% 花在学习「看到问题后该怎么回答」。

IGNORE_INDEX = -100 这是 PyTorch nn.CrossEntropyLoss 的默认「忽略标签」——任何 target 位置等于 -100 的，那一项的 loss 直接取 0，也不反传梯度。不用自己写 mask，框架已经帮你做了。

二、核心方法 _encode()：6 步走流程

输入：一条 messages 列表（JSONL 一行，典型是 3 轮：system / user / assistant）。
输出：{"input_ids": [...], "labels": [...]} 或 None（如果被截断没剩下回答）。

1

拼「完整对话」→ 字符串 full

full = tok.apply_chat_template(messages, tokenize=False)

用 tokenizer 自带的 chat template（千问 2.5 有自己的 <im_start>/<im_end> 格式），把 messages 数组拼成一大段带角色标记的文本。这一段包含了完整的 system + user + assistant 回答。

<im_start>system
你是一个能干的助手<im_end>
<im_start>user
解释牛顿三定律<im_end>
<im_start>assistant
牛顿第一定律：惯性定律...<im_end>
2

拼「只有 prompt 前缀」→ 字符串 prefix

prefix = tok.apply_chat_template(messages[:-1], tokenize=False, add_generation_prompt=True)

这里有个极其精妙的小技巧：messages[:-1] 表示「去掉最后一条（assistant 回答）」，只保留 system + user。然后加 add_generation_prompt=True 就是在末尾再插一个 <im_start>assistant\n——这正好是推理时模型开始生成之前你喂给模型的前缀，长度就是「prompt 占了多少 token」。

<im_start>system
你是一个能干的助手<im_end>
<im_start>user
解释牛顿三定律<im_end>
<im_start>assistant
← 到这里为止！后面回答部分不算。
3

分别 tokenize，得到 full_ids 和 pre_ids

full_ids = tok(full, add_special_tokens=False)["input_ids"]
pre_ids = tok(prefix, add_special_tokens=False)["input_ids"]

因为 full 字符串的前缀部分和 prefix 字符串逐字完全相同（template 一样，chat 历史一样），所以 tokenize 出来的前半段也是逐 token 相同的。于是 len(pre_ids) 就是「prompt 占用的 token 数」n_pre。

为什么不用字符串长度来算？因为 BPE tokenizer 不是按字符切的（"Apple" 可能是 1 个 token，也可能是 2 个），必须用 tokenizer 真跑一遍才知道准确的分界位置。这是 99% 的 SFT 新手都会踩的坑：用字符串长度估分界，结果 mask 多/少一两个 token，训练效果悄悄变差还不自知。

4

超长截断 & 无效样本过滤

如果 full_ids 长度超过 max_len（默认 512），就截前 512 个。然后：

n_pre = min(len(pre_ids), len(full_ids))
if n_pre >= len(full_ids): return None # 回答全被截掉了，直接丢

这是个防御性检查：如果截断之后剩下的全是 prompt、连一个 assistant 的 token 都没留下，那这条样本完全没信号，直接丢掉。

5

✨ 核心：构造 labels，mask 掉前 n_pre 个位置

labels = full_ids.copy()
labels[:n_pre].fill_(IGNORE_INDEX)

这就是 SFT 的灵魂代码，也是 你要写的 TODO 4。先复制一份，然后把前 n_pre 个位置全部填成 -100。

位置索引 i
labels[i] = -100（不算 loss）
labels[i] = input_ids[i]（算 loss）
6

返回字典 {"input_ids": full_ids, "labels": labels}

注意 input_ids 全程没变过，模型推理时依然需要完整的 prompt + 回答作为输入（CausalLM 做 shift 用）。改的只有 labels 数组的前半段内容，input_ids 保持原样。

三、配套函数：collate() —— batch padding 也要 mask

一个 batch 里每条样本长度不一样，DataLoader 会把它们 pad 到最长那条。padding 位置同样不能算 loss，所以 collate() 里也做了对称处理：

字段真实内容部分padding 部分
input_ids原 token idpad_id（千问一般是 151643）
labels原样（前半 -100，后半 token id）-100 ✅ 同样忽略
attention_mask10（让注意力不看 padding 位置）

漏了 padding 的 -100 会怎样？模型会被梯度"教"去预测 pad token，表现为生成时偶尔会吐出一些奇怪的 pad id 字符。这也是新手常见坑之一。

六、FAQ：新手容易搞混的几个问题


  

    为什么 input_ids 不改，只改 labels？
    
模型的 forward 依然要完整的 input_ids 才能做自回归 shift（HF 内部还是 logits[:,:-1] vs labels[:,1:]）。前半段 prompt 的 token 对 attention 计算依然有用——模型需要看到 user 的提问才能正确预测后面的回答，不能把 input_ids 也截掉，只需要让那些位置「不产生 loss」就行，所以只动 labels。

  


  

    -100 是在哪被忽略的？我没在代码里看到判断。
    
在 PyTorch 自带的 F.cross_entropy / nn.CrossEntropyLoss 里，它有个默认参数 ignore_index=-100。也就是说只要你不手动改这个参数，任何 target 值为 -100 的位置，那一项 loss 自动计 0，并且对应梯度也为 0。这个约定是 PyTorch 官方定的，所以几乎所有框架（HF、trl、peft）都沿用这个魔法数字。

  


  

    我直接用 messages[:-1] 做 prompt，assistant 那条的内容做 target，用 encoder-decoder 的方式训不行吗？
    
理论上可以，但 decoder-only 的 GPT 类模型标准做法就是「拼一起 + labels mask」，因为 decoder-only 架构没有 encoder，它所有的上下文只能在同一个序列里通过注意力看到。而且你用 encoder-decoder 做法也需要把 prompt 喂进 decoder 做 kv cache，和拼一起的信息量其实等价，还多了跨实现兼容性的坑。统一用 decoder-only 的 CausalLM mask 方式，业界所有工具链（HF、LoRA、DPO、GRPO）都支持，这是事实标准。

  


  

    如果是多轮对话（system/user/asst/user/asst 共 5 条）呢？
    
apply_chat_template 同样支持多轮，它会把 5 条 messages 按格式串起来成一大段。然后 messages[:-1] 会保留前 4 条（最后一条 asst 之前的全部），add_generation_prompt 再加最后一轮 <im_start>assistant\n—— 这个 template 技巧不管前面多少轮都能用，计算出的 n_pre 就是「除了最后一轮 assistant 回答以外所有部分的 token 数」。注意：当前这个简单版本只会对「最后一轮 assistant」算 loss，前面轮次的 assistant 回答会被一起 mask 掉。更进阶的做法是多轮 SFT（所有 assistant 段都算 loss），思路一样——逐段找出所有 assistant 段的起止位置，把段外全标 -100，段内保留真实 token id。

  


  

    为什么 add_generation_prompt=True 必须加？不加会怎样？
    
chat template 的 add_generation_prompt=True 会在末尾加 <im_start>assistant\n（千问格式）或者 <|assistant|>（Llama 格式）这类「模型要开始说话了」的标记。如果不加，prefix 的长度比实际喂给模型推理时的前缀少了这一两个特殊 token，结果就是 assistant 回答开头的标记被当成训练目标——模型会在训练时学会先输出 <im_start>，推理时因为你已经手动加了它，就会出现输出重复的开始符号，表现为生成开头多了一些奇怪的字符。
